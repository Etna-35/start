# MAX Chrono Bot

Текстовый MAX-бот для личного хронометража предпринимателей.

Человек в течение дня пишет короткие записи («20 минут говорил с поставщиком»),
бот сохраняет действия, вечером просит оценить каждое по **A/B/C/D**, считает
статистику дня и формирует личный вывод. Отдельно есть **обезличенная**
статистика сообщества — без имён и без текстов конкретных действий.

> MVP. Голосовые сообщения, speech-to-text, аудио и загрузка файлов **не реализованы** — только текст.

---

## Что умеет бот

| Команда / действие | Что делает |
|---|---|
| `/start` | Приветствие и описание приватности |
| `/agree` | Согласие, создание профиля |
| `20 минут разбирал финансы` | Запись действия (парсинг длительности + категория) |
| `/today` | Список действий за сегодня с нумерацией |
| `1A 2B 3D` | Оценка действий из последнего списка |
| `/summary` | Итог дня: минуты и проценты по A/B/C/D + вывод |
| `/community` | Обезличенная агрегированная статистика сообщества |
| `/export` | Текстовый экспорт за 7 дней (только свои данные) |
| `/delete_today` → `УДАЛИТЬ СЕГОДНЯ` | Удаление записей за сегодня |
| `/delete_me` → `УДАЛИТЬ МЕНЯ` | Удаление профиля и всех записей |
| `/admin_stats` | Только для роли `admin`; агрегаты, без личных текстов |
| `/help` | Справка |

Каждый вечер (по таймзоне пользователя, по умолчанию 22:30 Europe/Moscow) бот
сам присылает список неоценённых действий за день.

### Смысл оценок
- **A** — задачи собственника (стратегия, финансы, ключевые переговоры, найм, продукт).
- **B** — полезная управленческая работа (контроль, согласования, рабочие переписки с результатом).
- **C** — операционка, которую стоит делегировать/регламентировать.
- **D** — слив времени, хаос, отвлечения.

---

## Приватность (главный принцип)

- Пользователь видит **только свои** конкретные действия.
- Администратор **не видит** личные тексты действий по умолчанию.
- Сообщество видит **только обезличенные агрегаты** (`/community`).
- Конкретные тексты и оценки пользователя **не попадают** в общий отчёт.

Эти гарантии заданы конструктивно в `app/services/privacy_service.py` и
`app/services/community_stats_service.py` (в этих пайплайнах вообще нет
поля с текстом действия) и покрыты тестами `tests/test_privacy.py`.

## Архитектура

```
app/
  main.py                       # FastAPI app + запуск планировщика
  config.py                     # Pydantic Settings (env)
  db.py                         # engine + session_scope
  models/                       # SQLAlchemy 2.x: user, time_entry, review_session, parse_error
  schemas/
    dto.py                      # IncomingMessage (нормализованное сообщение)
    max_update.py               # извлечение сообщения из сырого MAX Update  ← точка адаптации
  repositories/                 # users, time_entries, review_sessions, parse_errors
  services/
    max_client.py               # изолированный клиент MAX Bot API
    message_router.py           # маршрутизация intent → ответ
    duration_parser.py          # парсер длительности (без LLM)
    review_parser.py            # парсер оценок A/B/C/D
    category_classifier.py      # keyword-классификатор категорий
    review_service.py           # списки/оценки/итог дня поверх БД
    summary_service.py          # минуты, проценты, rule-based вывод
    community_stats_service.py  # обезличенные агрегаты
    privacy_service.py          # экспорт + админ-агрегаты (без текстов)
    scheduler.py                # APScheduler: вечерний тик по таймзонам
  handlers/                     # commands, text_entries, reviews, admin
  api/                          # webhook.py, health.py
alembic/                        # миграции
tests/                          # duration / review / summary / privacy
```

**Webhook-first.** `POST /webhook/max` проверяет secret (если задан), быстро
возвращает `200`, передаёт событие в `message_router`. Тяжёлой работы в вебхуке
нет; обработка синхронная, но изолирована так, что её легко вынести в очередь.
Один некорректный апдейт никогда не роняет вебхук (всё логируется).

## Запуск через Docker (рекомендуется)

```bash
cp .env.example .env          # впишите MAX_BOT_TOKEN и при желании MAX_WEBHOOK_SECRET
docker compose up --build
```

Compose поднимает Postgres и приложение, прогоняет `alembic upgrade head`
и стартует сервис на `http://localhost:8000`.

Проверка: `curl http://localhost:8000/health` → `{"status":"ok"}`.

Миграции вручную (если нужно):
```bash
docker compose exec app alembic upgrade head
```

## Локальный запуск без Docker

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env           # DATABASE_URL → ваш локальный Postgres

alembic upgrade head
uvicorn app.main:app --reload
```

Тесты (БД не требуется — логика чистая):
```bash
pytest
```

## Тестирование без токена MAX (dev-консоль)

Пока бот на проверке и токена нет, можно прогонять **весь** путь
«сообщение → роутер → БД → ответ» локально. `scripts/dev_console.py` подменяет
сетевой клиент MAX на фейковый (печатает ответы в терминал), но использует
настоящую логику и базу.

```bash
docker compose up -d db        # поднять только Postgres
DATABASE_URL=postgresql+psycopg2://chrono:chrono@localhost:5432/chrono \
    python scripts/dev_console.py
```

Дальше пишешь как пользователь: `/start`, `/agree`, `20 минут разбирал финансы`,
`/today`, `1A 2B`, `/summary`, `/community`. Спец-команды консоли: `:user <id>`
(сменить пользователя — удобно проверять приватность между людьми), `:name`,
`:raw` (показать сырой MAX-update), `:quit`.

Токен нужен только для **реальной** доставки сообщений через серверы MAX —
вся остальная разработка и тестирование идут без него.

## Подключение к MAX (webhook и dev-режим)

1. Получите токен бота и впишите `MAX_BOT_TOKEN` в `.env`.
2. Выставьте публичный HTTPS-URL на `POST /webhook/max` (например, через
   reverse-proxy или туннель). Зарегистрировать вебхук можно методом
   `MaxClient.set_webhook(url)` или вручную через MAX API.
3. (Опционально) задайте `MAX_WEBHOOK_SECRET` — тогда входящие запросы должны
   присылать его в заголовке `WEBHOOK_SECRET_HEADER` (по умолчанию
   `X-Max-Bot-Api-Secret`), иначе `403`.

**Dev/polling.** Архитектура webhook-first, но обработка апдейта изолирована в
`message_router.handle_update(update, session)`. Чтобы сделать polling-режим для
локальной отладки, достаточно отдельного скрипта, который периодически дёргает
`GET /updates` у MAX и передаёт каждый апдейт в `handle_update` — бизнес-логику
менять не нужно.

## Что адаптировать под реальную схему MAX Update

Вся завязка на формат MAX сосредоточена в двух файлах:

- **`app/schemas/max_update.py`** — извлечение `IncomingMessage` из сырого
  апдейта. Сейчас разбирается MAX/TamTam-подобная структура
  (`update_type=message_created`, `message.sender.user_id`, `message.body.text`,
  `message.recipient.chat_id`, плюс `bot_started`). Если реальные поля другие —
  поправьте только пути к ключам здесь.
- **`app/services/max_client.py`** — отправка сообщений
  (`POST /messages?user_id=...&access_token=...`, тело `{"text": ...}`) и
  `set_webhook` (`POST /subscriptions`). Если эндпоинты/авторизация отличаются —
  меняйте только этот клиент.

Остальной код работает с нормализованными `IncomingMessage` и ответами-строками,
поэтому не зависит от точной схемы MAX.

## ENV переменные

См. `.env.example`. Ключевые:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | строка подключения к Postgres |
| `MAX_BOT_TOKEN` | токен бота (только из env) |
| `MAX_WEBHOOK_SECRET` | секрет вебхука (если задан — проверяется) |
| `WEBHOOK_SECRET_HEADER` | имя заголовка с секретом |
| `MAX_API_BASE_URL` | базовый URL MAX Bot API |
| `DEFAULT_TIMEZONE` | таймзона по умолчанию (`Europe/Moscow`) |
| `DAILY_REVIEW_HOUR` / `DAILY_REVIEW_MINUTE` | время вечернего запроса (в таймзоне пользователя) |
| `SCHEDULER_ENABLED` | включить/выключить планировщик |
| `ADMIN_MAX_USER_IDS` | список `max_user_id` админов через запятую |
| `LOG_LEVEL` | уровень логирования |

## Тесты

`pytest` покрывает обязательные по ТЗ области:

- `test_duration_parser.py` — все форматы длительности (мин/час/полчаса/полтора часа/час, длительность в начале и в конце, `None` без времени).
- `test_review_parser.py` — `1A 2B 3D`, `1 A, 2 B, 3 C`, `1-А 2-Б 3-Д`, `1а 2б 3д`, латиница/кириллица, и распознавание «это оценки, а не действие».
- `test_summary_service.py` — суммы минут, проценты, выводы при A<20%, C>35%, D>15% (и сильный день / мало данных).
- `test_privacy.py` — в community-stats и admin-stats нет текстов действий; export возвращает только данные конкретного пользователя.

## Чего намеренно нет в MVP

Голосовые/аудио/STT, загрузка файлов, личный кабинет, оплата, рейтинги
участников, LLM-анализ, PDF-отчёты, сложная геймификация, наставники, открытый
просмотр чужих дневников.
